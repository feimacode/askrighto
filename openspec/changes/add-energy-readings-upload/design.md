## Context

The real file (checked 19 Nov 2026, aggregates only, kept local):

- NEM12 interval data. One `200` line: `200,<NMI>,E1,E1,E1,,<meter serial>,KWH,30,` (NMI, configuration, register, suffix `E1`, a blank data stream id, serial, unit, interval length). 364 `300` lines: date `CCYYMMDD`, 48 values, quality flag (`A` or `V`), empty reason code and description, an update timestamp, an empty load timestamp. Six `400` lines after two `V` days, giving interval ranges with a flag and a reason (`79` is a power outage).
- No `100` header and no `900` end line, so it is a distributor portal export (the file name ends `_UNITEDENERGY_VEC.csv`), not a full MDP file. The last line has 54 fields, not 55 (no trailing comma).
- 17 Feb 2026 has no record. Interval times are market time (Australian Eastern Standard Time, no daylight saving).
- 17,472 values, none empty or negative, about 2,665 kWh, about 7.3 kWh a day. A rough time-of-day split of this household is 9% midnight to 7am, 36% 7am to 3pm, 39% 3pm to 9pm and 16% 9pm to midnight (AEST clock).

How hosts pass data matters: tool inputs are flat strings and numbers (the strictest of the three hosts' rules), and a model that reads a 117 KB file and adds it up would break the rule that every figure comes from a lookup or a calculation the server owns.

## Decisions

1. **Two steps, one stateless server.** `summarise_interval_readings` turns the file text into a **profile string**; `compare_energy_plans` takes that string back as `readingsProfile`. The server keeps nothing between the two calls: the host carries the profile. This keeps rule 3 (no user data stored) and gives the model small, checkable numbers. A profile is about 1,100 numbers, not 17,000.
2. **What the profile holds.** For each calendar month and for weekdays and weekends: 48 half-hourly averages in kWh per half hour, in market time, plus the number of days that went into each. Also the period start and end, days present, missing dates (listed, at most 31), annual total kWh as measured, export (`B` stream) total if the file has one (all `E` streams count as main consumption; controlled load is a gap, see decision 6), and a count of intervals with a non-`A` quality flag or outage event. No NMI, no serial, no per-day values. It is encoded as compact JSON and passed as a single string with a format version; it is not signed or secret, and the server revalidates it on every use (ranges, counts, version).
3. **Costing from the profile.** Each plan's time-of-use windows (days and clock times) are converted from the household's local clock to market time using the postcode's state rules (no daylight saving in QLD; NSW, VIC, ACT and TAS shift an hour in summer; SA has its own half-hour offsets), and the share of use in each window is summed from the profile for each tariff period's dates. That gives the same `shares` the estimate already takes from a bill, so `calc.ts` keeps its maths; only the way shares are found changes, and plans whose windows cannot be mapped stay "not estimated" with the reason.
4. **Honesty about the period.** If the readings cover less than 365 days, the annual figure is scaled by days present, and the result says so, including missing dates. If they cover under 90 days, or miss a whole season of the plan's tariff periods, the tool says seasonal plans are less certain (no refusal, just the label).
5. **Basis and wording.** `Usage.basis` gains `"readings"`. The notice reads "from the household's own interval readings, 18 Nov 2025 to 17 Nov 2026", never "typical". The readings note from #45 is not shown when the basis is `readings`.
6. **Parsing rules.** Tolerant of what real exports do: missing `100` and `900`, a missing trailing field, blank reason fields, `V` days with `400` records, several `200` blocks. Strict about what would make figures wrong: a unit other than kWh, Wh or MWh (kVArh and similar are ignored, and Wh and MWh are converted), an interval length other than 5, 15 or 30 minutes (finer values are summed to 30 minutes), a value that is not a number, a `300` line without the right number of values for its `200` block, duplicate dates, and more than one NMI in one file (refused: one household at a time). Register mapping, from the AEMO National Metering Identifier Procedure (V5.1, effective August 2009, section 7 "Data Stream Suffix for Interval Metering Data", Table 1; Iven, 19 Nov 2026): the first character of the suffix says what the stream is, the second numbers the meter or element. **Every stream whose first character is `E` (master export kWh from the grid, that is, energy delivered to the household) is main consumption; every stream whose first character is `B` (master import kWh into the grid, that is, solar and other generation exported by the household) is solar export.** The procedure names them from the grid's side, so "import" is the household's export, a common source of mix-ups that the docs must spell out. Where several streams share a first character (`E1`, `E2`, `B1`, `B2`), they are summed. The averaged and check variants (`A`, `C` import; `D`, `F` export) are treated like `B` and `E` when they are the only ones present and never added to the master stream of the same kind (they duplicate it). The net stream (`N`, defined as E minus B) is accepted only when no `E` or `B` stream is present: consumption is then net of the household's own solar, solar export cannot be separated, and the result says so. **Controlled load is a gap by decision:** a controlled load circuit reported as `E2` is indistinguishable from main consumption, so all `E` streams are main consumption, the result lists controlled load under what is left out, and the controlled load rate is not applied. Reactive power (`J`, `K`, `L`, `P`, `Q`, `R`), apparent energy (`S`, `T`, `U`), power factor, `Q` and `H`/`Y` metering, and volts or amps streams are ignored. Numeric first characters (type 6 accumulation streams) are not interval data and are refused as NEM13-style data.
7. **Refusals.** NEM13 (`250` records): "this is an accumulation (meter reading) file with no half-hourly figures; ask for interval data". No consumption register, over the size cap (default 600,000 characters, about five times a year of data), or not NEM12: `needs_input` with what to ask for, no figures.
8. **Privacy.** The tool never logs its input (the framework already logs only error messages), returns no identifier, and the NMI is dropped before anything is built. Errors name the line number and the problem, never the content. The tool is read-only and `openWorldHint` false.
9. **Grounding.** The result's source is "The household's own interval readings, supplied by the user" with the as-of date set to the last interval date, and the parser's rules cite the MDFF specification (AEMO), re-stated in our own words. Figures are computed by the server, not narrated by the host.
10. **What it does not do.** No recommendation; the output stays "lowest estimate for the readings". Direct file upload waits until hosts offer it; the paste route is the only one.

## Risks / Trade-offs

- A 117 KB paste may be beyond some hosts' tool-argument limits or too long for a model to copy faithfully. Mitigation: the size cap and a clear error; open question on whether a host can pass the file another way. A model that truncates the text would give a short, labelled period, not wrong figures: the days-present count is shown.
- The profile is only as good as the model passes it on. It is revalidated server-side, but a changed profile is undetectable. This is information for one person's own comparison, not a stored record.
- Daylight saving and window conversion are easy to get wrong. Tests will use a synthetic file with known peaks across a daylight saving change and check each state.
- Averages by month and weekday hide holidays. Accepted for v1; labelled.
- Solar households: `B` export is reported and costed where the plan's feed-in is a single rate (as now); time-varying and capped feed-in stay listed as not estimated. Export per half hour is kept in the profile (a second set of 48 averages) only so a time-varying feed-in can be costed later; it is not used in v1.
- Controlled load is left as a gap: a household with a controlled load circuit will have that energy costed at the general rate, which can overstate or understate the cost. The result says controlled load is not costed separately.

## Findings from the build (19 Nov 2026)

- **Postcode on the first tool.** The profile is built on the household's local clock, so `summarise_interval_readings` also takes the postcode (the host already has it): daylight saving is applied per date for the state when the profile is built, and each plan's windows are then read directly. The design said the plan's windows would be converted to market time at comparison time; the result is the same and the comparison needs no state rules. `compare_energy_plans` checks the profile's state matches its postcode.
- **Shares per tariff period.** `Usage.sharesFor` gives a plan its shares from the months each tariff period covers; `calc.ts` takes them in place of a single split. The maths is unchanged.
- **Window times.** Retailers write end times both as the last minute (20:59) and as the end (21:00), and some as `2100`; all are read, anything not on a half hour is not estimated.
- **Check on a real file.** Iven's own file matches an independent calculation (see tasks 3.1).
- **Not tested on the three hosts** (task 1.3).
